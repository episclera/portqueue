# Citus driver

A distributed Postgres cluster behind the Citus coordinator, for sharded Postgres at
scale. It speaks the `pg` wire protocol like Postgres — `SKIP LOCKED` claiming,
`LISTEN/NOTIFY` wake-ups, `RETURNING`, and advisory locks — but its migrations declare
each table's **shard key** (usually the queue name) so rows co-locate on the right node.

## Connect

Point at the Citus coordinator — the same `pg` connection options as the Postgres driver:

```ts
import { PortQueue } from '@portqueue/core';
import { CitusDriver } from '@portqueue/core/drivers/citus';

const pq = new PortQueue({
  driver: new CitusDriver({
    connectionString: process.env.DATABASE_URL, // the Citus coordinator
    // or share an existing pg.Pool: { pool }
    // or pass raw pg config: { config: { host, user, password, database } }
  }),
});
await pq.init();
```

## Capabilities & notes

- **`SKIP LOCKED`** — yes. Contention-free claiming across many instances and nodes.
- **`LISTEN/NOTIFY`** — yes. Workers wake within milliseconds of an add.
- **`RETURNING`** — yes. Single-round-trip claims and inserts.
- **Advisory locks** — yes.
- **Distributed tables** — migrations declare each table's shard key rather than relying
  on unique constraints Citus can't enforce globally. Name-uniqueness and
  idempotency/singleton dedup are enforced in code, identically to every other engine.
- **Transactional enqueue** — use `fromPg(client)` or your ORM adapter, exactly as with
  Postgres. See [Transactions](../guides/transactions.mdx).

:::tip Optimization
The queue name is the distribution column, so keep work spread across many queues to
spread it across shards. Size the coordinator pool for the sum of worker concurrencies
and turn on [retention](../guides/retention.md) to keep the `job` table lean.
:::
