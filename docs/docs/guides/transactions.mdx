# Transactional enqueue

The classic **dual-write bug**: you write a business row, then enqueue a job — but the
process crashes between the two, or the write rolls back after the job was queued. Now a
job references data that doesn't exist (or vice-versa).

PortQueue fixes this by letting the insert join **your own** transaction. The job exists
**iff** your business write commits. The `NOTIFY` that wakes workers fires only **after**
commit.

:::tip Why we chose this
**PortQueue never opens, commits, or rolls back a transaction.** There is no
`pq.transaction(fn)` and no `pq.adoptTransaction(...)`. You start the transaction with
your own ORM/query-builder, wrap it with a small **adapter**, and pass it as `tx`. Your
code stays the single owner of commit/rollback.
:::

## Adapters from `@portqueue/core/tx`

An adapter exists for every supported client. Pick your tab:

<Tabs groupId="tx">
  <TabItem value="knex" label="Knex" default>

```ts
import { fromKnex } from '@portqueue/core/tx';

await knex.transaction(async (trx) => {
  await trx('order').insert(order);
  const fulfillment = pq.createQueue('fulfillment');
  await fulfillment.addJob({ data: { orderId }, tx: fromKnex(trx) });
}); // the developer's trx owns commit/rollback
```

Adapters ship for the query builders `fromKnex`, `fromKysely`, `fromDrizzle`; the ORMs
`fromPrisma`, `fromTypeorm`, `fromSequelize`, `fromMikroOrm`; and the raw clients
`fromPg`, `fromOracle`, `fromBetterSqlite3`, and `fromNodeSqlite`.

When no `tx` is passed, the method runs autonomously in its own short transaction. Every
producing method (`addJob`, `addJobs`, `removeJob`, `removeSchedule`, …) accepts `tx`.
