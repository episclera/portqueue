# Dashboard

`@portqueue/dashboard` is a pluggable React ops dashboard — queues, jobs, schedules, instances and
live stats. [Mount it on your existing HTTP server](#mount-on-an-existing-app) (Express, Koa,
Fastify, NestJS or raw Node), or [serve it from the CLI](#serve-it-from-the-cli-no-app-changes) with
no app changes at all.

## Pages

Navigation lives in a left sidebar (it collapses behind a burger button on small screens), with
links to these docs and the GitHub repo pinned at its foot, and the live-updates control and the
light/dark toggle in the top bar. Every page opens with a full-width subheader carrying its title,
a one-line description, and the page's actions.

The screenshots below follow the theme you are reading in — switch it in the top-right and they
swap with the rest of the site.

## Mount on an existing app

Install the dashboard package alongside `@portqueue/core`:

```bash
npm install @portqueue/dashboard
```

:::info Your driver's client is still required
The dashboard reads through a `@portqueue/core` driver, so its client (`pg`, `better-sqlite3`,
`@electric-sql/pglite`, …) must be installed too — otherwise PortQueue throws `MissingPeerDependencyError`.
:::

Create the dashboard once from your running PortQueue, then mount it with the adapter for your
framework — Express, Koa, Fastify, NestJS and raw Node all ship in the box.

<Tabs groupId="http-framework">
  <TabItem value="express" label="Express" default>

```ts
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({ portQueue: pq, basePath: '/portqueue' });

// `basePath` is the mount point, so the middleware goes on at the root.
app.use(dash.express());
```

  </TabItem>
  <TabItem value="koa" label="Koa">

```ts
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({ portQueue: pq, basePath: '/portqueue' });

app.use(dash.koa());
```

  </TabItem>
  <TabItem value="fastify" label="Fastify">

```ts
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({ portQueue: pq, basePath: '/portqueue' });

await app.register(dash.fastify());
```

  </TabItem>
  <TabItem value="nestjs" label="NestJS">

```ts
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({ portQueue: pq, basePath: '/portqueue' });

// Nest's default platform is Express, so mount it as functional middleware.
// No @nestjs/* dependency is required — but keep forRoutes in sync with basePath.
export class DashboardModule implements NestModule {
  configure(consumer: MiddlewareConsumer): void {
    consumer.apply(dash.nest()).forRoutes('/portqueue');
  }
}
```

  </TabItem>
  <TabItem value="node" label="Raw Node">

```ts
import { createServer } from 'node:http';
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({ portQueue: pq, basePath: '/portqueue' });

const handler = dash.node();
createServer((req, res) => {
  if (handler(req, res)) return; // the dashboard served this request
  // …fall through to your own routing
}).listen(3000);
```

  </TabItem>

`portQueue` is the only required option. `basePath` defaults to `/portqueue`, and `logger` (default
`console`) is where the dashboard reports the one problem it can only notice at startup: a missing
client bundle, which otherwise serves a placeholder with a 200 and looks like a working deploy.

:::info `basePath` is the mount point
It tells the dashboard where its own assets and API sit, so it must match where you mount the
adapter. Only NestJS repeats it — keep `forRoutes(...)` in sync.
:::

:::danger The dashboard ships no authentication
Anyone who can reach the mount can pause queues, remove jobs and delete schedules. **Protecting it
is your application's job** — see [Protecting the dashboard](#protecting-the-dashboard) below.
:::

## Protecting the dashboard

The dashboard has **no authentication of its own**, and no read-only mode: anyone who can reach the
mount can pause queues, retry and remove jobs, and delete schedules. Guarding a mount is something
your application already does, so **bring your own middleware and run it in front of the adapter** —
the same session, SSO or API-key check that protects the rest of your admin surface. Anything that
runs first and can end the response works; the dashboard only ever sees what got past it. Shipping a
second, weaker mechanism alongside yours would only invite people to rely on it.

No auth layer to reuse? HTTP Basic in front of the mount is enough for an internal tool —
[`basic-auth`](https://www.npmjs.com/package/basic-auth) parses the header and its README has the
middleware; compare the credentials with `timingSafeEqual` from `node:crypto`, terminate TLS in front
of it, and rate-limit the mount if it is reachable from the internet. Or skip your app entirely and
let the CLI host the dashboard — it brings its own Basic auth, below.

## Serve it from the CLI (no app changes)

If you'd rather not touch your app, the CLI hosts the dashboard as a standalone process. It
opens its own short-lived connection from `--driver` + `--connection-string` (or `DATABASE_URL`)
and serves the same UI.

The CLI is the one case with no host application to put a guard in front of, since it opens the
port itself — so **it brings its own HTTP Basic auth**, and credentials are required: pass
`--root-user` / `--root-password` or set `PORTQUEUE_ROOT_USER` / `PORTQUEUE_ROOT_PASSWORD`. The
bind defaults to `--host 127.0.0.1` (loopback only), with `--port 4321` and
`--base-path /portqueue`:

```bash
portqueue dashboard --driver postgres \
  --connection-string "$DATABASE_URL" --port 9000 \
  --root-user admin --root-password "$PORTQUEUE_ROOT_PASSWORD"
```

:::info Wrap the connection in a small script
So you don't retype the connection on every command, put it in a one-line shell script and call
that instead — see [Reuse the connection with a script](./cli.md#reuse-the-connection-with-a-script)
on the CLI page.
:::

## Docker

You don't need to containerise your app to run the dashboard — the CLI image can host it
as its own service. Pass the connection via `DATABASE_URL` and expose the dashboard `--port`.

```dockerfile title="Dockerfile"
FROM node:22-alpine
WORKDIR /app

# Install the CLI plus the client for your driver — it's an optional peer dependency,
# so pick the one you use: pg (Postgres), mysql2, oracledb, …
RUN npm install -g @portqueue/cli pg

EXPOSE 9000
# Serve the dashboard. DATABASE_URL and the dashboard credentials
# (PORTQUEUE_ROOT_USER / PORTQUEUE_ROOT_PASSWORD) are supplied at run time (see below).
ENTRYPOINT ["portqueue", "dashboard", "--driver", "postgres", "--port", "9000"]
```

```bash title="Serve the dashboard"
# Build the image once.
docker build -t portqueue-dashboard .

# Run it: pass the connection string and dashboard credentials, publish the port.
docker run --rm -p 9000:9000 \
  -e DATABASE_URL="postgres://user:pass@db:5432/app" \
  -e PORTQUEUE_ROOT_USER="admin" \
  -e PORTQUEUE_ROOT_PASSWORD="<your-password>" \
  portqueue-dashboard
```
