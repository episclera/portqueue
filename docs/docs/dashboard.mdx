# Dashboard

`@portqueue/dashboard` is a pluggable React ops dashboard — queues, jobs,
schedules, instances, and live stats — served from the CLI or mounted on your existing HTTP
server.

## Pages

Navigation lives in a left sidebar (it collapses behind a burger button on small screens), with
the live-updates control and the light/dark toggle in the top bar. Every page opens with a
full-width subheader carrying its title, a one-line description, and the page's actions.

- **Overview** — the activity cards for each job state, then the per-queue table with
  pause/resume.
- **Instances** — every registered instance with liveness, per-instance job counts, and
  per-instance pause/resume (only populated for servers that set an [instance key](./scale-horizontally.md#give-each-server-an-identity-key)).
- **Schedules** — recurring definitions across queues, with bulk unschedule.
- **Queue / Job detail** — drill into a queue's jobs or a single job.

### Tables

Every table works the same way:

- **`Results (n)`** in the card's top-left is the total number of matching rows in the database,
  not just the rows on screen.
- **Filters** opens a dialog of the filters that table supports; **search** sits next to it and
  matches that table's leading columns (queue name, schedule cadence, job id or status).
- **20 rows a page**, with numbered pagination at the bottom of the card.
- The page, the search term and the applied filters are all kept in the URL
  (`#/queues/emails?jobs.page=3&jobs.status=FAILED`), so any table view can be linked or
  reloaded.
- Rows are selectable where bulk actions apply (jobs, schedules); the **Bulk actions** button
  appears once something is selected.

:::note Searching jobs scans the most recent 500
Job ids have no text index, so a job search filters the most recent 500 jobs matching the other
filters rather than scanning the whole table. Narrow it with a status filter to reach older jobs.
:::

## Mount on an existing app

Install the dashboard package alongside `@portqueue/core`:

```bash
npm install @portqueue/dashboard
```

:::info Your DB driver's peer dependency is still required
The dashboard talks to your database through a `@portqueue/core` driver, so the driver's
client — an optional peer dependency — must be installed too: `pg` (Postgres),
`better-sqlite3` (SQLite), `@electric-sql/pglite` (PGLite), and so on. If it's missing,
PortQueue throws `MissingPeerDependencyError`.
:::

Create the dashboard once from your running PortQueue, then mount it with the adapter for
your framework — Express, Koa, Fastify, NestJS, or raw Node all ship in the box:

```ts
import { createDashboard } from '@portqueue/dashboard';

const dash = createDashboard({
  portQueue: pq,
  basePath: '/portqueue',
  auth: { mode: 'basic', username, password: process.env.PORTQUEUE_ROOT_PASSWORD },
});
```

:::info `basePath` must agree with the host framework's mount point
`basePath` is the URL prefix the dashboard lives under (default `/portqueue`). It's how the
dashboard knows where its own assets and API sit, so it **must match the path you mount the
adapter at** in your framework's router. The Express, Koa, Fastify, and raw-Node adapters read
`basePath` from the options and route themselves — just mount them at the root. NestJS is the
exception: you pass the same prefix to `forRoutes(...)`, so keep it in sync with `basePath`
(both `/portqueue` below).
:::

## Securing

The `auth` option guards access to the dashboard endpoint itself (never the DB). Three modes
are supported:

- **`none`** — no auth. Only for a trusted, locked-down network; the dashboard is fully open.
- **`basic`** — HTTP Basic auth against a fixed `username` / `password` (shown above).
- **`custom`** — supply your own `guard` for SSO, sessions, API keys, etc. It receives a
  framework-agnostic request (`{ method, url, headers }`) and returns either a boolean or an
  `{ authorized, readOnly? }` result — returning `readOnly: true` lets an authorized viewer in
  without control actions. The guard may be sync or async:

```ts
const dash = createDashboard({
  portQueue: pq,
  basePath: '/portqueue',
  auth: {
    mode: 'custom',
    async guard(req) {
      // `req` is { method, url, headers } — inspect a cookie, bearer token, header, etc.
      const token = req.headers['authorization'];
      const session = await resolveSession(token);
      if (!session) return { authorized: false };
      // Ops team gets full control; everyone else is read-only.
      return { authorized: true, readOnly: session.role !== 'ops' };
    },
  },
});
```

Always mount the dashboard behind your platform's auth in production, and rely on parameterized
queries.

## Serve it from the CLI (no app changes)

If you'd rather not touch your app, the CLI hosts the dashboard as a standalone process. It
opens its own short-lived connection from `--driver` + `--connection-string` (or `DATABASE_URL`)
and serves the same UI. Credentials are required: pass `--root-user` / `--root-password` or set
`PORTQUEUE_ROOT_USER` / `PORTQUEUE_ROOT_PASSWORD`. The bind defaults are `--host 127.0.0.1`,
`--port 4321`, and `--base-path /portqueue`:

```bash
portqueue dashboard --driver postgres \
  --connection-string "$DATABASE_URL" --port 9000 \
  --root-user admin --root-password "$PORTQUEUE_ROOT_PASSWORD"
```

:::info Wrap the connection in a small script
So you don't retype the connection on every command, put it in a one-line shell script and call
that instead — see [Reuse the connection with a script](./cli.md#reuse-the-connection-with-a-script)
on the CLI page.
:::

## Docker

You don't need to containerise your app to run the dashboard — the CLI image can host it
as its own service. Pass the connection via `DATABASE_URL` and expose the dashboard `--port`.

```dockerfile title="Dockerfile"
FROM node:22-alpine
WORKDIR /app

# Install the CLI plus the client for your driver — it's an optional peer dependency,
# so pick the one you use: pg (Postgres), mysql2, oracledb, …
RUN npm install -g @portqueue/cli pg

EXPOSE 9000
# Serve the dashboard. DATABASE_URL and the dashboard credentials
# (PORTQUEUE_ROOT_USER / PORTQUEUE_ROOT_PASSWORD) are supplied at run time (see below).
ENTRYPOINT ["portqueue", "dashboard", "--driver", "postgres", "--port", "9000"]
```

```bash title="Serve the dashboard"
# Build the image once.
docker build -t portqueue-dashboard .

# Run it: pass the connection string and dashboard credentials, publish the port.
docker run --rm -p 9000:9000 \
  -e DATABASE_URL="postgres://user:pass@db:5432/app" \
  -e PORTQUEUE_ROOT_USER="admin" \
  -e PORTQUEUE_ROOT_PASSWORD="<your-password>" \
  portqueue-dashboard
```
